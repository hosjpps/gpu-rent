# Введение

## Цель работы

Изучить структуру семестра и систему оценивания, определить роли и процесс работы, выбрать тему проекта по результатам исследования аналогов, сформулировать видение продукта и организовать репозиторий.

## Задание

1. Рассмотреть командную, исследовательскую и проектную составляющие семестра, недельные блоки и балльную систему.
2. Описать пять ролей, их ответственность и результаты работы.
3. Выбрать тему, сравнить аналоги и сформулировать исследовательские вопросы.
4. Определить возможности, границы и предварительный стек продукта.
5. Подготовить структуру репозитория, правила разработки и критерии готовности.

# Ход работы

## Структура семестра и оценивание

Семестр объединяет **командную работу**, **исследование** и **разработку**: распределение ответственности, проверку проектных гипотез и создание продукта. Для GPU Rent это организация пяти ролей, исследование корректного выделения GPU и биллинга, реализация БД и дальнейшая разработка веб-приложения.

Задание предусматривает **пять практических задач**. П1 и П2 оцениваются по пятибалльной системе. Для П3 и П4 применяется комплексная оценка качества работы над курсовым проектом и ответов преподавателю. Защита включает дополнительные вопросы, поэтому решения должны быть объяснимыми, а результаты — воспроизводимыми по исходникам и инструкциям.

Проект выполняет один студент — Васин С. А., группа ЭФБО-17-24. Он совмещает все пять ролей; отдельные участники команды не назначены. Задание требует командной работы, поэтому индивидуальный формат остаётся организационным ограничением: факт согласования этого формата с преподавателем здесь не утверждается.

Самопроверка после паузы не заменяет независимого ревью. До внедрения CI проверки БД выполняются вручную; демонстрация преподавателю дополняет контроль.

## Выбор темы и исследование

Тема — **GPU Rent, монолитное веб-приложение аренды облачных GPU-серверов**. Исследователям, студентам, разработчикам и специалистам по графике GPU нужны для обучения моделей, инференса, рендеринга и экспериментов. При кратковременной или нерегулярной нагрузке аренда позволяет использовать оборудование без его покупки и обслуживания.

Сравнение основано на публичных страницах и документации, использованных в исходном исследовании на 30.09.2026 [1–3]. Практическое тестирование сервисов не проводилось. Цены не сопоставляются: они зависят от оборудования, региона и тарифа.

Таблица 3 — Три аналога

| Сервис | Существенные особенности | Решение для проекта |
|---|---|---|
| RunPod [1] | GPU-поды, шаблоны окружений, диски и сетевые тома, API | Запуск из шаблона и постоянные тома |
| Vast.ai [2] | Площадка сторонних хостов; посекундная тарификация; хранение оплачивается и после остановки | Точный учёт времени и отдельный учёт хранения |
| Immers.cloud [3] | Виртуальные машины с GPU; посекундная оплата по заявлению сайта; готовые образы, API OpenStack | Каталог GPU и готовых окружений |

Выбор темы позволяет изучить транзакции, конкурентный доступ, временные диапазоны и безопасность данных. Сформулированы шесть исследовательских вопросов:

1. Как исключить одновременное выделение одной GPU?
2. Как обеспечить посекундный биллинг без повторных списаний?
3. Как масштабировать хранение журнала потребления?
4. Как согласовать баланс с журналом денежных операций?
5. Как исключить пересечение периодов цен?
6. Как изолировать данные разных клиентов?

Гипотезы проверяются в П3–П4 миграциями, конкурентными тестами и замерами запросов: используются ограничения и диапазоны, транзакции, секционирование и Row Level Security PostgreSQL [4].

## Видение, возможности и границы

Пользователь пополняет баланс, выбирает GPU и дата-центр, запускает инстанс из шаблона PyTorch, Jupyter или Stable Diffusion, подключается по SSH/Jupyter и оплачивает фактическое время работы. Администратор управляет оборудованием и ценами, отслеживает загрузку и выручку.

Предварительный MVP включает регистрацию и вход, SSH-ключи, каталог GPU и шаблонов, создание, остановку и терминацию инстанса, посекундный биллинг, пополнение и историю баланса, автоостановку при исчерпании средств, управление дата-центрами, нодами, GPU и ценами. API-ключи, сетевые тома, блокировка пользователей, дашборд и аудит отнесены к последующим версиям. Приоритеты уточняются в П2.

Реальная виртуализация не реализуется: команды запуска и остановки имитирует агент ноды. Интеграция с ЮKassa предполагает обработку webhook без реальных платежей. Предусмотрены тарифы on-demand и spot; правила вытеснения spot-инстансов уточняются в П2. Торговая площадка хостов, Windows-окружения, S3-хранилище и мобильное приложение находятся за границами проекта; веб-интерфейс планируется адаптивным.

![Рисунок 1 — Контекст системы GPU Rent](../diagrams/png/pr1-context.png)

Контекст включает гостя, клиента, администратора, биллинг-планировщик, агент ноды и внешний платёжный шлюз. Планировщик запускается раз в минуту, при этом стоимость рассчитывается по секундам фактического интервала.

Предварительный стек: монолит на Node.js 24 LTS, TypeScript и Express 4; React 18 с Vite; PostgreSQL 16; Redis 7 для кэша и сессий. Схема хранится в SQL-миграциях, доступ к данным планируется через node-postgres или Kysely. Монолит упрощает развёртывание и транзакции, PostgreSQL предоставляет нужные ограничения и секционирование. Деплой планируется на VPS через Docker Compose и Nginx с TLS; Nginx раздаёт клиентскую статику, Express обслуживает `/api`.

## Репозиторий и процесс разработки

В `docs/reports/` хранятся отчёты, `docs/diagrams/` — диаграммы, `db/` — миграции, данные, тесты и замеры, `tools/` — сборка, `reports/` — PDF; README содержит инструкции. БД реализована, сервер и клиент запланированы. Сейчас работа ведётся в `main` без CI; далее планируются ветки задач и pull request. Коммиты оформляются по Conventional Commits [5]. Готовность означает выполнение требования, применение миграций на чистой БД, успешные тесты, актуальную документацию, отсутствие секретов и воспроизводимость по README. Изменения проверяются перед слиянием; исходники SQL, Markdown и PlantUML сохраняются.
