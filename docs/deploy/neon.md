# Развёртывание БД на Neon

Neon даёт управляемый PostgreSQL без суперпользователя. Схема `gpu_rent` разворачивается на нём теми же миграциями
`db/migrations/0001–0014`, что и локально; отличается только способ запуска (скрипты `bootstrap_neon.sh` и `migrate.sh`).

Факты о Neon ниже взяты из документации neon.com/docs (страницы Connection pooling, Plans, Scale to zero, Roles,
Extensions) на дату подготовки документа; на страницах даты обновления нет. Всё, что касается лимитов и цен, помечено
«проверить в консоли»: тарифы меняются.

## Чем Neon отличается от локального PostgreSQL и как это учтено

| Отличие | Что делаем |
|---|---|
| Нет суперпользователя. Есть только роль-владелец проекта (по умолчанию `neondb_owner`) с CREATEROLE и CREATEDB. | Миграции выполняются под владельцем проекта; всё, что раньше требовало суперпользователя, свелось к одному условию (следующая строка). Других несовместимостей в 0001–0014 не найдено, миграции не менялись (в 0001 уточнён только комментарий). |
| В PostgreSQL 16 создатель роли получает только ADMIN OPTION, без INHERIT и SET. Поэтому `SET LOCAL ROLE gpu_rent_owner` и `CREATE SCHEMA ... AUTHORIZATION gpu_rent_owner` из 0001 падают с «must be able to SET ROLE». | `db/scripts/bootstrap_neon.sh` создаёт роли и выдаёт мигратору `GRANT gpu_rent_owner TO <мигратор> WITH INHERIT TRUE, SET TRUE`. Выдать это себе владелец может сам, потому что у него есть ADMIN OPTION. |
| Расширения: ставит владелец, а не суперпользователь. | `pgcrypto`, `btree_gist`, `citext` — trusted-расширения PG13+ и есть в списке Neon, `CREATE EXTENSION ... WITH SCHEMA gpu_rent` проходит у владельца БД. Владельцем расширений становится мигратор, а не `gpu_rent_owner`; их функции доступны PUBLIC, на работу приложения это не влияет. |
| `pg_stat_statements` в миграциях не создаётся. | Как и раньше: это настройка окружения. В таблице расширений Neon он есть; включение — `CREATE EXTENSION pg_stat_statements` отдельно, по желанию. |
| Есть direct и pooled endpoint (PgBouncer, режим transaction). | Миграции и администрирование — только через direct. `use_database_url` в `lib.sh` отказывается работать с хостом, в имени которого есть `-pooler`. Приложению pooled подходит: контекст пользователя ставится через `set_config(..., true)` внутри транзакции, `SET` на уровне сессии не используется. Настройки LOGIN-роли (`search_path`, таймауты) заданы через `ALTER ROLE ... SET`, они действуют и через пулер. |
| Роли, созданные через консоль или API Neon, получают членство в `neon_superuser`. Роли, созданные SQL-командой, не получают. | Роль приложения `gpu_rent_web` создаётся только SQL (`db/scripts/create_login_role.sh`). Скрипт проверяет, что у неё нет SUPERUSER, CREATEDB, CREATEROLE, REPLICATION, BYPASSRLS. |
| В PG16 CREATEROLE не может менять атрибуты, которых нет у него самого (REPLICATION, BYPASSRLS). | `create_login_role.sh` не задаёт эти атрибуты явно (у новой роли их и так нет): иначе повторный `ALTER ROLE` падал бы с «permission denied to alter role». Это нашла локальная имитация. |
| Compute засыпает после простоя, холодный старт. | `GET /api/health` не обращается к БД и не будит её; `?deep=1` будит. Приложение переживает обрыв соединения (обработчик `error` на пуле и на клиенте). |

## Пошаговая инструкция: пустой проект Neon до готовой БД

Нужны: `psql` 16 или новее и `bash` на машине, откуда выполняются команды; проект Neon с PostgreSQL 16 или новее (версия
выбирается при создании проекта; у проекта сейчас 18.6, миграции и SQL-тесты проверены на 16 и 18). Клиент `pg_dump` для
резервных копий должен быть не старее сервера (см. `.github/workflows/db-backup.yml`).

1. **Создать проект** в консоли Neon. Регион выбрать ближе к функциям Vercel. Запомнить имя БД (по умолчанию `neondb`)
   и роль (по умолчанию `neondb_owner`).
2. **Взять две строки подключения** (Connect в консоли), для одной и той же роли и БД:
   - **direct** — хост вида `ep-имя-123456.регион.aws.neon.tech`: для миграций, `bootstrap`, `create_login_role`, бэкапов;
   - **pooled** — тот же хост с `-pooler` после идентификатора endpoint (`ep-имя-123456-pooler.регион...`): для приложения.
   В обеих нужны `?sslmode=require` (Neon принимает только TLS). Строки, пароли и токены в репозиторий не кладём.
3. **Подготовить роли** (один раз), под владельцем проекта:
   ```bash
   export DATABASE_URL_DIRECT='postgres://neondb_owner:ПАРОЛЬ@ep-имя-123456.регион.aws.neon.tech/neondb?sslmode=require'
   db/scripts/bootstrap_neon.sh
   ```
   Создаёт `gpu_rent_owner`, `gpu_rent_app`, `gpu_rent_analyst` (NOLOGIN) и выдаёт мигратору членство в
   `gpu_rent_owner` с INHERIT и SET. Повторный запуск безопасен.
4. **Применить миграции** (тот же `DATABASE_URL_DIRECT`):
   ```bash
   db/scripts/migrate.sh --dry-run   # что будет применено
   db/scripts/migrate.sh
   ```
   Применяются только миграции, которых нет в `gpu_rent.schema_migrations`. БД не пересоздаётся. Повторный запуск
   пишет «схема актуальна».
5. **Создать LOGIN-роль приложения** SQL-командой (не через консоль Neon):
   ```bash
   export GPU_RENT_WEB_PASSWORD="$(openssl rand -hex 24)"   # без спецсимволов: пароль пойдёт в URL DATABASE_URL
   db/scripts/create_login_role.sh
   ```
   Роль `gpu_rent_web` становится членом `gpu_rent_app`; для неё заданы `search_path`, `statement_timeout = 15s`,
   `idle_in_transaction_session_timeout = 30s`. Повторный запуск меняет пароль.
6. **Загрузить демо-данные** (по желанию), под мигратором. Пароли `admin` и `demo` задаёт тот, кто грузит сид:
   ```bash
   DEMO_PASSWORD='…' ADMIN_PASSWORD='…' bash -c 'source db/scripts/lib.sh; use_database_url; psql_db -f db/seed/seed_demo.sql'
   ```
   Полный `seed.sql` на Neon не грузить: он занимает сотни мегабайт. `reset.sh` на Neon не запускать: он делает
   `DROP DATABASE`.
7. **Настроить приложение** (переменные окружения Vercel):
   - `DATABASE_URL` = **pooled** адрес с ролью `gpu_rent_web`: `postgres://gpu_rent_web:ПАРОЛЬ@ep-имя-123456-pooler.регион.aws.neon.tech/neondb?sslmode=require`. Пароль в адресе — без спецсимволов (`openssl rand -hex 24` из шага 5). Если в нём есть `/`, `+`, `=`, `#`, `@`, их нужно закодировать (`%2F`, `%2B`, `%3D`, `%23`, `%40`): иначе адрес не разбирается и все запросы к БД дают 500;
   - `ENC_KEY`, `WEBHOOK_SECRET`, `CRON_SECRET` и остальные — как в корневом `.env.example` и `server/src/config.ts` (полная инструкция по Vercel — [vercel.md](vercel.md));
   - `DB_POOL_MAX` оставить маленьким (по умолчанию 2): число соединений на Neon ограничено.
8. **Проверить**: `GET /api/health?deep=1` вернёт `"db":"ok"`; вход под demo; `GET /api/catalog/gpus`.

Переменные: `DATABASE_URL_DIRECT` (direct, владелец проекта) — для скриптов `db/scripts`; `DATABASE_URL`
(pooled, `gpu_rent_web`) — для приложения; `GPU_RENT_WEB_PASSWORD`, `DEMO_PASSWORD`, `ADMIN_PASSWORD` — разово при
подготовке БД. Скрипты разбирают URL в переменные `PG*` (пароль не попадает в аргументы процесса).

## Как обновлять схему

1. Новое изменение — новый файл `db/migrations/00NN_имя.sql` в том же стиле: `BEGIN; SET LOCAL ROLE gpu_rent_owner; ...;
   INSERT INTO schema_migrations (version) VALUES ('00NN_имя'); COMMIT;`. Уже применённые файлы не правим:
   `migrate.sh` их пропустит, и правка не дойдёт до БД.
2. Проверить локально: `db/scripts/reset.sh && db/scripts/test.sh`, затем `db/scripts/simulate_neon.sh` (имитация Neon,
   см. ниже).
3. Применить на Neon: `db/scripts/migrate.sh --dry-run`, затем `db/scripts/migrate.sh` через direct endpoint. До
   большой миграции сделать копию (`docs/deploy/backup_restore_check.sh`, `SRC_URL` — direct endpoint) или создать ветку
   Neon от текущего состояния (ветвление — возможность Neon, проверить в консоли ограничения тарифа).
4. Если миграция упала: файлы выполняются в одной транзакции, частичных изменений не остаётся; исправить файл (он ещё не
   записан в журнал) и запустить `migrate.sh` снова.

## Free-тариф: лимиты и что с ними делать

Цифры по документации Neon на момент подготовки; **проверить в консоли** (Billing / Plans) перед защитой и после
любых изменений тарифа.

- **Хранилище.** В документации сейчас указано 1 ГБ на проект (в комментарии `seed_demo.sql` — 0,5 ГБ, это более старая
  цифра; проверить в консоли). Демо-сид с 52 пользователями и 34 тысячами записей потребления занимает около 31 МБ вместе
  с системными таблицами (по `pg_database_size` в локальной имитации). Следить за ростом `usage_records` (потребление
  по инстансам, партиции помесячно) и `audit_log`: размер смотреть в консоли Neon.
- **CU-часы.** В документации: 100 CU-часов в месяц на проект (для compute 0,25 CU это около 400 часов).
  Без пользователей compute не спит полностью: БД будят собственные автоматические запуски (если заданы `APP_URL` и
  секреты): `billing-cron.yml` каждые 30 минут (48 раз в сутки), глубокая проверка `uptime.yml` раз в час (24),
  `db-backup.yml` раз в сутки (1) и Vercel Cron раз в сутки (1). Каждое пробуждение держит compute около 5 минут
  автосуспенда плюс время запроса (примем 5,1 мин). Оценка: 74 × 5,1 мин × 0,25 CU ≈ 1,6 CU-ч в сутки, то есть около
  47 CU-ч в месяц, почти половина лимита ещё до пользовательской нагрузки. На нагрузочные тесты и показ остаётся
  около 50 CU-ч. Если запаса не хватает, уменьшить глубокую проверку (раз в сутки или реже) или поднять шаг `billing-cron.yml`
  до 60 минут. Не ставить внешний мониторинг, который стучится в `/api/health?deep=1` чаще, чем нужно: каждый такой запрос
  будит compute. Обычный `/api/health` БД не трогает.
- **Засыпание.** На Free автосуспенд через 5 минут простоя, отключить нельзя (проверить в консоли). Первое обращение после
  паузы идёт дольше обычного: документация говорит о нескольких сотнях миллисекунд на пробуждение, плюс время на
  новое соединение приложения. Перед показом открыть приложение за минуту-две до начала. Таймаут подключения в приложении 5 секунд.
- **Соединения.** Лимит `max_connections` зависит от размера compute (по документации, для 0,25 CU около 104, часть
  зарезервирована под служебные нужды). Приложение ходит через pooled endpoint с маленьким пулом (`DB_POOL_MAX = 2` на
  экземпляр функции); при многих параллельных функциях Vercel пулер поглощает всплеск.
- **История восстановления.** На Free окно восстановления короткое (по документации 6 часов): полагаться на неё как на
  резервную копию нельзя. Для защиты и сдачи сделать `pg_dump` через `backup_restore_check.sh`.

## Что проверено в имитации и что нет

`db/scripts/simulate_neon.sh` создаёт на локальном PostgreSQL 16 роль-аналог `neondb_owner` (LOGIN, CREATEROLE, CREATEDB,
не суперпользователь, владелец БД `gpu_rent_neonsim`) и прогоняет `bootstrap_neon.sh`, `migrate.sh` (дважды),
`create_login_role.sh`, демо-сид и проверки под LOGIN-ролью. Подключение идёт по `DATABASE_URL_DIRECT`.
`--cleanup` удаляет БД и роли имитации.

Имитация **не** воспроизводит: TLS и пулер, лимиты и засыпание compute, список разрешённых расширений Neon, служебные
роли (`cloud_admin`, `neon_superuser` и атрибуты вроде BYPASSRLS у владельца), владельца схемы `public` в Neon-базе
(0001 делает `REVOKE ALL ON SCHEMA public FROM PUBLIC`; локально `public` принадлежит `pg_database_owner`, на Neon
**проверить**: если 0001 упадёт именно на этой строке, это место нужно будет править по сообщению об ошибке), работу приложения
через настоящий pooled endpoint.
